# Implementation Report — FASE 1: Quebra de blocos configurável + Controle de clima

**Data:** 24/09/2026
**Status:** COMPLETA — build OK, revisão aprovada

## Objective
Implementar a FASE 1 do plano do TableTop RPG (Fabric 1.21.11, Mojang mappings):
1. **Quebra de blocos configurável no menu do GM** (Settings): novo setting `playersCanBreakBlocks` (default `false`). O mestre sempre pode quebrar; jogadores só se liberado no menu E estiverem no turno deles.
2. **Controle de clima (sol/chuva/tempestade) pelo menu do GM**, sem comandos de chat.

## Scope / Subtasks
- **Subtarefa B** — Quebra de blocos configurável: setting no servidor + payloads C2S/S2C + toggle no menu.
- **Subtarefa C** — Controle de clima: payload C2S + handler no servidor + 3 botões no menu.

## What Changed
- `SessionManager`: novo campo `playersCanBreakBlocks` (default `false`) + getter/setter.
- `PlayerControlHandler.canBreakBlocks`: agora `isMaster || (canPlayersBreakBlocks && canPlayerAct)` (antes: só mestre).
- `RpgNetworking`: 4 novos payloads + registro + receivers + broadcast:
  - `BlockBreakSettingPayload` (C2S) — mestre libera/bloqueia a quebra.
  - `BlockBreakSettingQueryPayload` (C2S) — cliente pede o estado ao abrir Settings.
  - `BlockBreakSettingStatePayload` (S2C) — resposta à query / broadcast após mudança.
  - `WeatherSetPayload` (C2S) — 0=sol, 1=chuva, 2=tempestade.
  - Receivers validam `SessionManager.isMaster` (não-mestre é ignorado).
  - Clima aplicado via `ServerLevel.setWeatherParameters(...)`.
- `TabletopRpgClient`: campo `volatile playersCanBreakBlocks` + receiver S2C que atualiza o campo e a tela de Settings aberta.
- `RpgSettingsScreen`: botão toggle "Players quebram blocos: Sim/Não" + 3 botões "Definir clima: Sol/Chuva/Tempestade" + query do estado ao abrir; `backY` do mestre ajustado de `+68` para `+164`.

## Decisions
- **API de clima verificada com javap** (regra do projeto): em 1.21.11 a assinatura é `setWeatherParameters(int clearTime, int rainTime, boolean raining, boolean thundering)` — 4 args, não 5. Valores copiados do bytecode do comando vanilla `/weather`: sol=`(6000,0,false,false)`, chuva=`(0,6000,true,false)`, tempestade=`(0,6000,true,true)`.
- **Padrão de rede seguido**: mesmo padrão do `DayNightCycle` (payload C2S de set + query + state S2C; C2S valida mestre no servidor).
- **Broadcast S2C para todos** (não só mestre): consistente com `sendAuraStateToAll`/`sendHoverConfigToAll`; mantém o campo do cliente preciso para todos. Payload de 1 bool, inofensivo.
- **Sem sync de estado do clima no cliente** (decisão de escopo): o requisito é controle, não exibição. Botões são ações com rótulo "Definir clima: X" para não parecerem estado atual.
- **Clima afeta só a dimensão atual do mestre**: mesmo comportamento do `/weather` vanilla (sem efeito no Nether/End). Limitação aceita, não bug.
- **`canBreakBlocks` no cliente retorna `true`** (deixa passar): o servidor decide — padrão já existente no projeto (evita cancelar o clique antes do pacote chegar ao servidor).

## Remaining Issues
- **Race toggle × resposta da query** (pré-existente, mesmo padrão do botão de ciclo): se o mestre clicar no toggle antes da resposta da query, o label pode piscar. Estado final sempre correto (pacotes processados em ordem por conexão).

- **Sem sync de clima no cliente**: os botões não refletem o clima atual ao reabrir Settings (decisão de escopo).

## Lessons / Memory
